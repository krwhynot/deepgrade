# DeepGrade 5.0.0 — Stakeholder Brief

**Audience:** customers and executive sponsor
**Period covered:** 16–30 July 2026
**Prepared:** 30 July 2026
**Status: NOT RELEASED.** The shipping version is still **4.31.0**. Nothing described below
has reached a customer yet.

---

## The short version

We put the DeepGrade plugin through a full safety review before shipping a major version, and
it failed that review in ways our own tests had been reporting as fine. We have been fixing
that. The release is deliberately held until the work is verified rather than merely finished.

**The single most useful sentence in this document:** our test suite was green the entire time
these defects existed. Finding that out is what the last two weeks bought.

---

## What was actually done

A structured hardening programme against the plugin, covering 33 known issues, executed in
staged batches with an independent reviewer checking our work at each stage.

**Independent verification.** Rather than self-certifying, every stage was reviewed by a
separate AI system from a different vendor, deliberately instructed to try to disprove our
claims. It ran four review rounds and produced 31 findings. **We refuted none of them** — every
one we tested was confirmed. That is an uncomfortable result and it is the right kind of
uncomfortable: an outside check that never finds anything is not a check.

## What this prevents for customers

These are real defects found and fixed, not hypotheticals. Each one would have reached
customers in a 5.0.0 release built on our previous confidence:

| Problem found | What a customer would have experienced |
|---|---|
| Quality-gate setup wrote its configuration to a location the tool never reads | You would set up automated code checks, be told it succeeded, and get no checks. Silently. |
| Plan-status command misread a standard project layout | "No plans found" on a perfectly normal setup, with your plans sitting right there |
| Export feature relied on a tool absent from stock Windows | Export failing on Windows machines |
| A cleanup command reported an error on success | Confusing failure messages on runs that actually worked |
| Several skills could never activate | Features shipped that could not run at all |
| Commands pointed at a capability we had removed | Instructions telling you to run something that no longer exists |

## The finding that mattered most

Partway through, we stopped testing the plugin and started testing **the tests**.

The method is simple: deliberately break something, then check whether the tests notice. If
they stay green, the test was decorative.

They stayed green far more often than expected. We found tests that:

- confirmed a Windows fallback existed, while the fallback created nothing
- checked that a safety guard was *present*, never that it *worked*
- contained a probe that could not fire under any circumstances
- checked that a heading existed rather than that the feature behind it did

None of this was visible by reading the code. All of it appeared only under deliberate
breakage. The suite now includes checks that run the actual commands and inspect the actual
results, plus cases that verify the tests stay quiet on legitimate changes — because a test
that cries wolf gets deleted, and then you have nothing.

## Why the release is being held

Two weeks in, our internal record said more was complete than truly was. We have corrected that
count **downward twice**, on evidence, and expect one further correction.

That is not a setback. Publishing a version whose safety checks are decorative would be the
setback. The count now matches reality, and reality is the only useful input to a ship decision.

The remaining work falls into three buckets:

1. **Verification that needs a human** — installing the plugin and confirming the safety hooks
   fire in a real session. Roughly 20 minutes of the owner's time; it is the highest-value
   remaining action.
2. **A small number of open decisions** requiring owner sign-off, documented with options and
   trade-offs.
3. **Behaviour that text inspection cannot verify.** Some requirements are about whether an
   instruction is *followed*, which no amount of file scanning can establish. Our reviewer's
   guidance, which we have adopted: record those honestly as unverified rather than issue a
   green check that means less than it appears to.

## What "better" will mean, concretely

When 5.0.0 ships:

- Setup instructions point at locations the tool genuinely reads
- Commands work on Windows and Linux, not just the development machine
- Every shipped capability can actually activate
- Failures are visible instead of silent
- The safety checks have been proven able to fail, one at a time — so a green result is evidence
  rather than decoration

## Honest limitations

- **No customer has received any of this.** Version 4.31.0 remains current.
- **No firm release date.** It ships when the remaining verification passes, not on a calendar.
- **Some requirements will ship marked "not verified by automated means."** This is deliberate.
  We would rather label the gap than paper over it.
- **This document reflects 30 July 2026.** The review process is ongoing and further findings
  are expected — which is the intended behaviour of the process, not a failure of it.
