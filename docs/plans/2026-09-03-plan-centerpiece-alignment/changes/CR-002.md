# CR-002: Invert the plan — build the instrument first, let it produce the inventory

Date: 2026-09-03
Author: Kyle (decision), agent (record)
Supersedes: `spec.md` revision 2 § Scope (the asserted 40-line / 12-file
inventory), § Delivery (phase order), FR-2, FR-4, NFR-4, and the go/no-go table.

## What Changed

**The order of work is inverted.** Revision 2 derived an inventory by hand, then
wrote phases against it, then planned to build a guard last to enforce the
result. That order makes the inventory a *claim*.

Under CR-002 the guard is built **first**, in its own phase, with a shipped
self-test. Its output **is** the inventory. Nothing counts scoring sites by hand
at any point.

New order:

1. **Build the instrument.** Pattern plus its self-test, committed as a runnable
   file in the repository — not asserted in prose. Ships in **report mode**: it
   enumerates violations and exits 0, so the suite stays green while violations
   still exist.
2. **The instrument enumerates.** Run it, commit its output as the inventory
   artifact. This replaces the Scope section's hand-counted table.
3. **Fix what it found**, grouped by whatever its output actually shows.
4. **Flip report mode to enforce mode.** Now any surviving violation fails
   Layer 1.

## Why It Changed

The design gate returned NOT PASS twice. The second audit named the cause
precisely:

> The instrument is asserted, not shipped. Line 176 adopts "instrument self-test
> before measurement"; line 206 reports an 11-assertion self-test. Neither the
> pattern nor the test exists anywhere in the plan folder, so `46 of 114` and the
> `40` derived from it are unfalsifiable.

That is correct, and it is the `EVIDENCE-MISSING` class the gate exists to catch.

**Six counting errors were made across two attempts, all the same shape** — a
number asserted, no instrument shipped, the number wrong:

| # | Error | Direction |
| --- | --- | --- |
| 1 | `RED` matched inside `REQUIRED`; a stage file appeared to hold 11 hits and holds 0 | too broad |
| 2 | Pattern matched `/40` but not `N/5`; 4 hits missed in one file | too narrow |
| 3 | `score_history` reported as "exactly twice repo-wide"; the grep covered three subtrees | too narrow |
| 4 | `awk` does not treat `\b` as a word boundary; gave 5 where `grep` gives 31 | tool mismatch |
| 5 | Verification greps tripped on markdown bold, reporting false misses | too literal |
| 6 | Pattern requires a digit numerator, so `X/40` at `quick-plan.md:72` was missed | too narrow |

Errors 2 and 6 are the same defect discovered twice, three hours apart. A
seventh is likelier than a clean seventh attempt. **The fix is not a better
pattern — it is to stop asserting patterns.**

The inversion also dissolves three separate problems that were being patched
individually:

- **Revision 1's headline defect** — the guard reddening Layer 1 on sites no
  phase scheduled — cannot occur. The guard is built before the fixes and ships
  in report mode, so there is no window in which it fails on unscheduled work.
- **Revision 2's S14 finding** — reverting Phase 1 after Phase 4 restores
  vocabulary the enforcing guard rejects — cannot occur either, for the same
  reason. Enforce mode is the last commit; revert order is unconstrained before it.
- **The Scope section's out-of-scope list** stops being a judgment call defended
  in prose and becomes an explicit exclusion list *inside the instrument*, which
  the self-test covers.

## Impact on Other Phases

Every phase in revision 2's Delivery is replaced. The new shape:

| Phase | What | Risk |
| --- | --- | --- |
| 0 | Build the instrument + self-test, ship in report mode | LOW |
| 1 | Run it; commit the output as the inventory | LOW |
| 2 | Delete `/toque:codex-challenge` (CR-001, unchanged) | MEDIUM |
| 3+ | Fix what the instrument enumerated, grouped by its output | LOW |
| last | Flip report → enforce; mutation test proves it bites | LOW |

**Requirements:** FR-1, FR-5, FR-6, FR-7 stand. FR-2 restated above. FR-4
restated: the guard's subject set and exclusions are derived and self-tested,
and it has two modes. FR-3/FR-3a remain withdrawn by CR-001.

**Success metrics:** the "40 → 0" target is withdrawn — 40 was the unfalsifiable
number. Replaced by "the instrument reports zero violations in enforce mode",
which is measured by the instrument rather than asserted about it.

**What this does not fix.** The inversion removes counting errors. It does not
make the *exclusion* judgments automatic: deciding that the readiness scan's
letter grades are a different product is still a human call. It is now recorded
in code with a test rather than in prose, which makes it reviewable, not correct.

## Verification constraint

The `plan-auditor` agent used for both previous gates is **no longer available
in this session**. A third gate attempt cannot repeat the same mechanism. Two
substitutes are available and both are weaker than the original:

- The instrument itself carries much of what the audit was checking, and unlike
  the audit it is re-runnable by anyone.
- The Codex CLI (0.153.0, installed) can review adversarially, as it did for the
  first design — though CR-001 deletes the packaged version of that workflow.

This is recorded as a limitation rather than worked around. The next gate is
weaker than the two that failed, and a pass under it means less.
