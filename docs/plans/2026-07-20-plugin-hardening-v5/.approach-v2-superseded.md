## 2. Options Analysis

Three execution strategies were evaluated against the verified dependency data.

### Option A — Wave-based incremental, tests interleaved *(SELECTED)*

Nine ordered waves derived from the mandatory-sequencing constraints, with test additions landing **inside** the
wave that creates the behavior they verify. Work starts at the independent island (F29+F31) and the true dependency
root (F17), neither of which waits on any decision.

**Pros:** Honors every hard sequencing constraint (F17→F01, the 4a/4b/4c hooks sequence, F05→F26, F33→F16, F18+F19
together, F12 at the end of Phase 6). Each wave is independently revertible **pre-release**. The red suite clears
early (Wave 3), restoring a trustworthy signal before the risky hooks epic. Test additions land with their behavior,
so the 94% blind spot closes progressively rather than at the end.
**Cons:** More commits and branch coordination. `GUIDE.md` (touched by 11 findings) must be serialized through one
branch regardless of wave. Longest calendar time.
**Risk: LOW.** **Rollback: LOW *pre-release only*** — per-wave revert is source control, not deployed recovery.
Post-release recovery is governed by §8 and is identical for all three options.

### Option B — Big-bang single branch

All 36 items on one branch, one review, one release.

**Pros:** Single review pass; no intermediate states where docs and behavior disagree; fastest raw throughput.
**Cons:** Collides head-on with R3 — the suite is blind to 31 of 33 findings and *enshrines* two (F22, F23), so a
big-bang branch runs mostly unverified, and Layer 2 goes structurally red the moment hooks move. A regression
surfaces with 36 changes to bisect. F12 alone relocates 1,528 lines into 10 files, and the bootstrapping constraint
means the workflow driving the work would be edited mid-flight.
**Risk: HIGH.** **Rollback: HIGH** (all-or-nothing revert of a 60+ file diff).

### Option C — Critical + high only, defer the 26 mediums

Fix F01–F06 and ship.

**Pros:** Smallest diff, fastest to a correct-loading plugin, lowest regression surface.
**Cons:** Leaves the phantom references, the `$1` argument-injection bug, the stale self-description, and the
duplication in place — so the plugin still misleads users, just in fewer places. Worse, it leaves F24's fail-open
hole *unconditional* (wiring the scripts in F06 converts it from conditional to always-on), which means shipping
Option C alone is a net **security regression**. Would require an immediate second release.
**Risk: MEDIUM.** **Rollback: LOW.**

### Comparison matrix

Scored 1–5, higher is better.

| Criterion | A — Waves | B — Big bang | C — Critical only |
|-----------|:---------:|:------------:|:-----------------:|
| Implementation ease | 3 | 2 | **5** |
| Timeline | 2 | 3 | **5** |
| Strategic value | **5** | 4 | 1 |
| Risk profile | **5** | 1 | 2 |
| Rollback complexity | **5** | 1 | 4 |
| **Total** | **20** | 11 | 17 |

### Decision rationale

**Option A wins on risk profile and rollback — the two criteria that dominate here** because of one verified fact:
*the existing test suite catches 2 of 33 findings and actively asserts two of the defects as correct behavior.*
When the safety net is that thin, the ability to revert one wave rather than a 60-file diff is worth more than
calendar speed.

Option C scores well on ease and timeline and is genuinely tempting, but it is **disqualified on correctness, not
preference**: F06 wires the orphaned scripts, which converts F24's fail-open parsing from a jq-absent edge case into
the only code path. Shipping the highs without the mediums therefore ships a guard that fails open unconditionally.
The dependency data makes F24 non-optional in the same batch — so the minimal *safe* scope is already larger than
Option C's boundary.

Option B's throughput advantage is illusory against a blind test suite. Its single review pass is exactly what
R3 says cannot be trusted.

**Would revisit if:** a hard external deadline appears → fall back to Option C **plus F24** (never F06 without F24) as
a deliberate partial release, with the remainder tracked. If a POSIX CI runner materialises and the suite gains real
coverage of the blind classes, Option B's risk profile improves enough to reconsider for a future release.

## 3. Locked Decisions

### 3.1 Hook source of truth *(open question 1 — REVISED after adversarial review, v2)*

> **v1 retracted.** The first version of this decision hardcoded exec form with a bare `bash` launcher and claimed
> drifted features were "restored by construction." Both were wrong. See §3.1.1–§3.1.3.

`scripts/tq-*.sh` become canonical **after** they are brought up to the behavior union (§3.1.2). Create
`hooks/hooks.json` and delete the inline `hooks` key from `plugin.json` **in the same commit** — atomicity is
mandatory, not stylistic: with both a `hooks/` folder and a manifest `hooks` key present, Claude Code v2.1.140+
**silently ignores the folder** and loads from the manifest, warning only in `claude plugin list`.

#### 3.1.1 Launcher contract — UNPROVEN, resolved by Wave 0 gate G0

**Verified on this host:** `bash` is **not resolvable from PATH** in a PowerShell/system context. It exists only at
`C:/Program Files/Git/bin/bash.exe`. Git Bash *is* installed.

v1's reasoning was backwards. It chose exec form partly to avoid the documented PowerShell fallback — but `shell`
form is what invokes Claude Code's **own Git Bash detection** (`shell` "defaults to bash, or to powershell on Windows
when Git Bash isn't installed"), while exec form with `"command": "bash"` **bypasses that detection** and resolves
from the PATH that lacks `bash`. Exec form is therefore the *more* likely form to fail here, not less.

Neither form is proven. **No cutover happens until gate G0 passes:**

| Candidate | Mechanism | Status |
|-----------|-----------|--------|
| Shell form | Relies on Claude Code's Git Bash detection | Unproven — plausible primary |
| Exec form, `"command": "bash"` | Resolves from PATH | **Verified to lack `bash` on this host** |
| Exec form, discovered absolute interpreter | Explicit path to `bash.exe` | Unproven; not portable to POSIX without indirection |

**Gate G0 experiment:** build a throwaway probe plugin in scratchpad with one `SessionStart` handler that writes a
marker file; launch `claude --plugin-dir <probe>` **from PowerShell, not Git Bash**; assert the marker exists. Repeat
per candidate form. If only shell form fires, this decision flips to shell form. If none fires, the decision is void:
the inline `hooks` key stays and Wave 4 reduces to applying F22/F24/F25 inline.

### 3.2 `plan.md` disposition *(open question 2 — resolved, upgraded to a correctness defect)*

Split into `skills/plan/SKILL.md` (router, under 500 lines) plus one bundled file per phase.

This is **not** tidiness. Skill content enters the conversation once and is never re-read, and after auto-compaction
Claude Code re-attaches only **the first 5,000 tokens of each skill**. At 16–19K tokens, Phases 5–9 of `plan.md` are
silently discarded mid-workflow — in exactly the long sessions a 9-phase workflow produces. (The audit's ~26K figure
was overstated; the structural conclusion is unchanged since both far exceed the 5,000-token floor.)

The brainstorm's worry about changing invocation is **resolved as a non-issue**: `skills/plan/SKILL.md` in a plugin
named `toque` yields `/toque:plan`, byte-identical to today. Independently reinforced — the official
slash-commands page now 301-redirects to the skills page, and the authoring guide states *"Custom commands have been
merged into skills… Use `skills/` for new plugins."*

Authoring constraints: references exactly **one level deep** (a second hop risks silent `head -100` partial reads),
anchored with `${CLAUDE_SKILL_DIR}`, forward slashes only. Phase 5's four sub-templates stay **inside**
`phase-5-audit.md`. The Step 0 boundary disagreement between the two decompositions (F12 starts phases at line 248
and never assigns Step 0; the research router assigns it) is reconciled **before** implementation.

### 3.3 Troubleshooting technique canonicality *(open question 3 — decided by plan owner)*

**`toque-plugin/docs/troubleshooting-techniques/` is canonical.** The standalone
`troubleshooting-skill/resources/techniques/` becomes **generated output**, produced by
`scripts/build-standalone-skill.sh` and gated by `tests/layer5-drift-check.sh`
(`git diff --no-index --exit-code`).

Chosen because `troubleshooting-skill/` is **confirmed not a git repository and not tracked by the plugin repo** —
verified directly, not assumed. Making it canonical would place the source of truth permanently outside version
control, unreviewable and invisible to the test suite. This option keeps everything in git, honors the "no new
skills" non-goal (unlike the in-plugin-skill variant), and makes drift structurally impossible rather than merely
detectable.

**Hard cost, accepted:** all 9 files have drifted across 296 lines with genuine one-sided content on **both** sides.
A naive generate-from-one-side destroys content. The reconciliation is **one manual pass, file by file**, folding the
skill's distilled runtime prose (canonical for technique content) into the plugin copy while dropping the
planning-era "Status Before Implementation" / "Implementation" sections, and preserving the plugin's `Plan` linkage
field that the skill's `kb-schema.md` lacks. Only then does generation begin.

Symlinks were **disqualified** on three independently verified silent-failure modes: a sibling directory resolves
outside the marketplace and is skipped for security, `core.symlinks=false` in this repo, and default Git Bash
`ln -s` silently copies. Submodules were rejected because whether the marketplace cache recurses them is
undocumented — the failure mode is an empty skill directory shipped to every installer.

**Strip the bare MCP names; keep explicit closed `tools:` allowlists** (adding the `Write`/`Bash` entries F02/F07
require).

Hardcoding qualified names is firmly rejected: the server segment is chosen by the *installing user*. Three distinct

### 3.6 Versioning *(open question 4 — resolved)*

**Ship as `5.0.0`.** The structural moves are *not* breaking (hooks relocation has no invocation surface;
`plan.md` → `skills/plan/` preserves the name). What justifies MAJOR is **hook denial semantics**: F24's fail-closed
branch newly blocks actions that previously succeeded. F22 (deny → ask) and F25 (permit `--force-with-lease`) are
loosenings and do not themselves force a major bump.

A **4.x migration note is required** — third-party marketplaces have auto-update **off by default**, and hooks keep
the old version's path mid-session. The note carries the four-command sequence:
`/plugin marketplace update toque-marketplace` → `/plugin update toque` → `/reload-plugins` → `/plugin list`.

**Operationally decisive:** the version *is* the cache key. Without the `plugin.json` bump, none of this hardening
reaches a single existing user, silently and with no error.

## 4. Approach / Pattern

**Pattern: Strangler Fig with an interleaved test harness, executed in dependency-ordered waves.**

Each subsystem is replaced behind a stable interface while the old implementation stays live until its replacement is
proven: `hooks/hooks.json` supersedes the inline block atomically; `skills/plan/` supersedes `commands/plan.md` with
the invocation name preserved; generated technique files supersede hand-maintained duplicates. The user-facing
surface (`/toque:*` names, install identifiers) never changes.

**Why this pattern and not a rewrite:** every defect here is a *wiring* defect, not a design defect. The audit
confirmed the structural skeleton is spec-correct — 80 verified strengths, passing `claude plugin validate`, correct
component layout, near-textbook skills. Rewriting would discard working structure to fix what is fundamentally a set
of broken references. Strangler fig preserves the 80 strengths while replacing the drifted wiring.

**Critical adaptation:** the classic pattern assumes a trustworthy test suite. This one has 6% coverage of the target
defects and asserts two of them as correct. So test additions are treated as **part of each wave's definition of
done**, not as a follow-up — and the exact HEAD baseline (**100 pass / 4 fail**, corrected in v2 — the earlier 156
figure wrongly summed the suite with the 41 assertions `run-all.sh` never executes) is recorded first so "expected red" stays
distinguishable from "new red."

## 5. Top 3 Risks

### R1 — The hooks epic is one indivisible commit that opens a security hole mid-flight
**Impact: HIGH.** F06+F23 must land as a single commit spanning 13–16 files. The instant the scripts are wired,
F24's fail-open parsing goes from a jq-absent edge case to **the only path** — every blocking guard (force-push,
migration, database-deploy) fails open for any command containing a quote. Fixing F24 afterward means shipping a live
security regression.
**Mitigation:** Wave 4 steps 1–3 are one reviewable unit with a hard gate — the F24 fail-closed tests must pass in the
*same commit* that wires the scripts. Fail closed on the three blocking guards; keep the four informational hooks
fail-open. `TQ_STRICT_GIT` defaults off so the stricter guards cannot strand the maintainer mid-plan.

### R2 — The test suite is blind to 31 of 33 findings and enshrines two of them
**Impact: HIGH.** Coverage is 2/33 (~6%), including **zero** coverage of the sole critical and all five highs. Layer 2
Test 5 asserts `exit 2` *and* stderr containing `"WARNING"` — locking in the exact contradiction F22 reports — and
Layer 2 extracts hooks by **positional index** from inline `plugin.json`, so it is structurally welded to the
architecture F23 removes. Both go red by design.
**Mitigation:** interleave test additions with the waves that create the behavior. Rewrite Layer 2 inside the F06/F23
epic, never after: de-index extraction, flip Test 5 to `exit 0` + `permissionDecision: "ask"`, add
`--force-with-lease` negative tests, and run every case **twice — with and without `jq` on PATH**. Land the four
highest-value assertions early (name uniqueness, filename↔`name:` agreement, `tools:` shape, reverse reference sweep);
they cover the critical, all five highs, and F24/F25.

### R3 — Bootstrapping: `commands/plan.md` is both the running workflow and finding F12
**Impact: MEDIUM-HIGH.** F12 deletes the file and relocates 1,528 lines into 10 new ones — while that file is driving
this plan.
**Mitigation:** the dependency data independently forces F12 last (it depends on F14, F15, F16, F19, F20 and breaks
two test files), so ordering and constraint agree. Before Wave 7, pin a copy
(`git show 4fb4b64:commands/plan.md > <scratchpad>/plan-pinned.md`) and drive remaining phases from it. Wave 7 does
not begin until Phases 3–8 of this plan are complete. **Never leave both `commands/plan.md` and `skills/plan/SKILL.md`
live**, even briefly — two components resolving to `/toque:plan` reproduces the F30 duplicate-entry defect.

serialization, the release-ships-to-nobody trap, and edits outside version control.)*

## 8. Release Rollback & Recovery *(NEW in v2 — v1 had none)*

> v1 offered only "per-wave revert," which the adversarial review correctly scored 1/5. That describes **source
> control, not deployed recovery**, and it contradicted this plan's own analysis: the version *is* the plugin cache
> key, so once a user has cached `5.0.0`, a `git revert` reaches them **never**. v1 cited that fact to justify the
> version bump and then failed to apply it to recovery.

### 8.1 Why revert is not rollback

An installed plugin lives in a versioned cache directory, and third-party marketplace auto-update is **off by
default**. Reverting the repository changes what a *future* installer receives; it does nothing for anyone already
running the bad version. There is no "unpublish."

### 8.2 Forward rollback is the actual mechanism

Recovery ships **forward** as `5.0.1`, never backward:

1. Revert the offending commits on `main`.
2. Bump `plugin.json` to `5.0.1` (a new cache key — without the bump nothing propagates).
3. CHANGELOG entry naming the regression and the affected version.
4. Publish, then instruct users: `/plugin marketplace update toque-marketplace` →
   `/plugin update toque` → `/reload-plugins` → `/plugin list` to confirm.

**Precondition:** this path must be *rehearsed* in Wave 8 before tagging (§8.5), not attempted first during an

### 8.3 Kill switch — recovery without a release

A misbehaving guard must be disableable in seconds. Every guard script honors a single environment variable:

```bash
[ "${TQ_DISABLE_GUARDS:-}" = "1" ] && exit 0    # first executable line of each blocking guard
```

Scope: the guards that can **deny** — the git guard and the migration guard. Informational hooks are unaffected
(they cannot block work). Documented in README and the migration note. The unconditional fallback remains
`/plugin uninstall toque`.

### 8.4 State-file compatibility

The inline and script tracker implementations write **different keys** (`total` vs `total_changes_since_audit`), so a
user mid-session can hold a stale-schema temp file. Every reader must tolerate both and treat a missing/unparseable
key as `0` rather than erroring. State files are disposable by design — deleting `tq-*` temp files is always a safe
recovery step, and that must be stated in the migration note.

### 8.5 Rollback rehearsal — Wave 8 gate

Before tagging `5.0.0`: install the built plugin from the marketplace into a scratch profile, confirm the hooks fire,
then execute the full `5.0.1` forward-rollback sequence end to end and confirm the scratch profile returns to prior
behavior. **A rollback path that has never been executed is not a rollback path.**
