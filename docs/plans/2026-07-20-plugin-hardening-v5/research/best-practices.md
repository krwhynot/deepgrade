# Question 1 — Hook placement, executable bits, cross-platform behavior, and exit-code semantics

## The question

For a Claude Code plugin, should hook behavior live in `hooks/hooks.json` referencing `${CLAUDE_PLUGIN_ROOT}/scripts/*.sh`, or inline in `plugin.json`? What does the spec say about each, how should executable bits and cross-platform (Windows Git Bash + POSIX) be handled, and what are the per-event stdout/stderr surfacing and exit-code-2 semantics?

## Recommendation

**Migrate to `hooks/hooks.json` referencing bundled scripts via exec form with an explicit `bash` launcher, and delete the `hooks` key from `plugin.json` entirely.**

### 1. Both forms are legal; only one is idiomatic

The plugins reference states the location as "`hooks/hooks.json` in plugin root, or inline in plugin.json", and the manifest schema types `hooks` as `string|array|object` — "Hook config paths or inline config". So inline is not deprecated. But every other signal in the docs points at the file:

- The File-locations table lists **Hooks → `hooks/hooks.json`** as the default location.
- The canonical plugin directory tree shows `hooks/hooks.json` plus `hooks/security-hooks.json`.
- The hooks reference says: "Define plugin hooks in `hooks/hooks.json` with an optional top-level `description` field."
- The migration guide's before/after table maps "Hooks in `settings.json`" → "Hooks in `hooks/hooks.json`".
- `claude plugin init --template hooks` scaffolds "A `hooks/hooks.json` with a sample event handler".
- The `hooks` manifest field's own example value is `"./my-extra-hooks.json"` — the field exists to add *extra* paths, not to be the primary home. `hooks/hooks.json` is auto-discovered with no manifest entry.

Two capability differences favour the file: `hooks/hooks.json` supports a top-level `description` field (the inline object form has no such slot), and it can be split across multiple files.

### 2. Critical gotcha — you cannot keep both

Path behavior rules: "When a plugin has both a default folder and the matching manifest key, Claude Code v2.1.140 and later warns about the ignored folder in `claude plugin list` and the `/plugin` detail view. The plugin still loads using the manifest paths."

So if DeepGrade adds `hooks/hooks.json` while retaining the inline `hooks` object in `plugin.json`, **the new file is silently ignored** and only a warning surfaces. The migration must be atomic: create the file and remove the key in the same commit.

### 3. Executable bits — DeepGrade has a live latent bug

Official troubleshooting says hooks not firing is caused by "Script not executable → Run `chmod +x script.sh`", and step 1 of hook debugging is `chmod +x ./scripts/your-script.sh`.

**[UNVERIFIED — no primary source]** (Tier C, local inspection): on disk the eight `scripts/*.sh` are `-rwxr-xr-x`, but `git ls-files -s scripts/` reports mode **100644** for all eight. Marketplace installs are git clones, so every installing user receives non-executable scripts. Fix with `git update-index --chmod=+x scripts/*.sh`.

**Better still, make the exec bit irrelevant.** Invoke through an explicit interpreter in exec form:

```json
{ "type": "command", "command": "bash",
  "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/dg-git-guard.sh"], "timeout": 5 }
```

This solves three problems at once:

- (a) `bash file.sh` does not require the exec bit.
- (b) The docs recommend it independently: "Prefer exec form for any hook that references a path placeholder. Exec form passes each `args` element as one argument with no shell tokenization, so paths with spaces or special characters need no quoting" — load-bearing on Windows where `${CLAUDE_PLUGIN_ROOT}` expands under `C:\Users\...\.claude\plugins\`.
- (c) It pins the interpreter, which matters because of the next point.

### 4. Cross-platform: the `shell` default is the real Windows risk

The command-hook schema says `shell` "Defaults to `\"bash\"`, or to **`\"powershell\"` on Windows when Git Bash isn't installed**."

DeepGrade's current hooks are all `bash -c '…'` shell-form strings. On a Windows host without Git Bash they are handed to PowerShell, where `bash -c '...'` fails outright — all five hook events break. Exec form with `"command": "bash"` at least fails loudly and identifiably rather than being mangled by the wrong shell (note `shell` is "Ignored when `args` is set", so exec form supersedes it). A genuinely bash-free Windows host still needs bash; the honest options are to declare Git Bash a prerequisite in the README, or ship parallel `.ps1` scripts selected by a `shell`-aware second hook entry.

**[UNVERIFIED — no primary source]** (Tier C, general Git/Windows engineering knowledge — the official docs are silent on line endings): also add `.gitattributes` with `*.sh text eol=lf` — CRLF line endings produce `bad interpreter: /bin/bash^M`. The scripts are currently LF-clean (verified via `cat -A`), but nothing enforces that on clone under `core.autocrlf=true`, which is the Windows default.

### 5. Per-event stdout/stderr — DeepGrade has three real surfacing bugs

The rule for exit 0: "For most events, stdout is written to the debug log but not shown in the transcript. The exceptions are `UserPromptSubmit`, `UserPromptExpansion`, and `SessionStart`, where stdout is added as context that Claude can see and act on."

- **SessionStart** — stdout *is* context. DeepGrade's `echo "[DeepGrade] Active plan: …"` works. But its jq-missing warning goes to **stderr** on exit 0, which is not documented as surfaced anywhere. That warning is almost certainly invisible today. Move it to stdout, or use `hookSpecificOutput.additionalContext`.
- **Stop** — stdout goes to the debug log only. DeepGrade's `echo "[DeepGrade] Session: $C files changed."` on stdout is **invisible**. The documented channel is `hookSpecificOutput.additionalContext`, which Stop/SubagentStop accept "for non-error feedback that continues the conversation". Notably the orphaned `scripts/dg-session-stop.sh` writes to stderr instead — also not a documented surfacing channel on exit 0, so neither variant currently works.
- **PreCompact** — stdout is debug-log only, and PreCompact supports **only** the top-level `decision: "block"` pattern, not `additionalContext`. There is no documented way to show a non-blocking PreCompact message. DeepGrade's PreCompact hook is functionally dead weight; either drop it or accept it as debug-only.
- **PreToolUse** — stdout debug-only; stderr surfaces via the exit-2 block path, which DeepGrade uses correctly.

### 6. Exit code 2 semantics (official table)

`PreToolUse` blocks the tool call; `Stop`/`SubagentStop` prevent stopping and continue the conversation; `PreCompact` blocks compaction; `UserPromptSubmit` blocks and erases the prompt; `PostToolUse` cannot block (shows stderr to Claude, tool already ran); `SessionStart` cannot block ("Shows stderr to user only" — that stderr "renders in the transcript as a `<hook name> hook error` notice… Claude doesn't see it, and the session proceeds").

Also: "Claude Code treats exit code 1 as a non-blocking error and proceeds with the action… If your hook is meant to enforce a policy, use `exit 2`."

**Bug found:** DeepGrade's Bash guard prints `"[DeepGrade] WARNING: git reset --hard discards changes."` then `exit 2` — which *blocks* the command. The message says warning, the behavior is a hard block. Either reword to BLOCKED or exit 0 with `additionalContext`.

### 7. The scripts are orphaned

**[UNVERIFIED — no primary source]** (Tier C, local inspection): `plugin.json` never references `${CLAUDE_PLUGIN_ROOT}` or `scripts/` at all — all logic lives in inline `bash -c '…'` one-liners using the `'"'"'` quote-escaping idiom nested inside JSON strings. Meanwhile eight maintained-looking `.sh` files sit unused and have already drifted: `dg-session-stop.sh` contains test-verification logic ("N files changed but no tests ran") that the inline Stop hook lost entirely. This is the strongest practical argument for migrating — it collapses two divergent implementations into one testable set of files.

### Secondary note on state files

The `/tmp/dg-*` session state files work under Git Bash but not under a PowerShell fallback. The docs warn that `${CLAUDE_PLUGIN_ROOT}` "changes when the plugin updates… treat it as ephemeral and don't write state there" and provide `${CLAUDE_PLUGIN_DATA}` for persistence. For per-session ephemeral counters `/tmp` is defensible; `${CLAUDE_PLUGIN_DATA}` is the portable choice.

### Net

Option A. The migration is mechanical, the scripts already exist and are better than the inline code, and it fixes a shipped bug (non-executable scripts on clone) plus three silent-output bugs. The main cost is one breaking-ish release and the need to test on a Git-Bash-less Windows host.

# Question 2 — Decomposing the 1,529-line `/deepgrade:plan` command

## The question

For the DeepGrade plugin's 1,529-line `/deepgrade:plan` slash command driving a 9-phase workflow: what do the official Anthropic docs say about command size, and what is the idiomatic decomposition — Agent Skill with progressive disclosure, multiple namespaced commands, or bundled files via `${CLAUDE_PLUGIN_ROOT}`? What are the invocation/UX tradeoffs of a command vs a skill for a user-initiated multi-phase workflow?

## Recommendation

**Convert `commands/plan.md` into `skills/plan/SKILL.md` (a router under 500 lines) plus one bundled reference file per phase, referenced exactly one level deep and anchored with `${CLAUDE_SKILL_DIR}`.** This is not a choice between the three approaches in the question — the idiomatic answer combines the skill move and the bundled-file reference, and rejects the namespaced-command split.

### Four findings that decide this

**1. The command-vs-skill tradeoff no longer exists.** The official docs now state: "Custom commands have been merged into skills. A file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way." The plugin-authoring page marks `commands/` as legacy: "commands/ | Plugin root | Skills as flat Markdown files. **Use `skills/` for new plugins**." So the UX question is moot. `skills/plan/SKILL.md` in a plugin named `deepgrade` produces `/deepgrade:plan` — byte-identical to what `commands/plan.md` produces today. Zero user-facing change, zero muscle-memory break, no marketplace or docs churn. Conversion is pure upside: you gain a directory for supporting files, invocation control, and per-skill `model`/`effort`/`paths`/`hooks` frontmatter.

**2. The size limit is explicit and doubly stated.** "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files" appears as a Tip in the Claude Code skills doc and again verbatim under "Token budgets" and in the pre-ship checklist on the skill-authoring best-practices page ("SKILL.md body is under 500 lines"). At 1,529 lines, `plan.md` is ~3x over. The best-practices page gives the direct instruction for this case: "If workflows become large or complicated with many steps, consider pushing them into separate files and tell Claude to read the appropriate file based on the task at hand."

**3. This is a correctness bug, not just untidiness — and it is the strongest argument.** Two documented runtime behaviors compound:

- "When you or Claude invoke a skill, the rendered SKILL.md content enters the conversation as a single message and stays there for the rest of the session… Claude Code does not re-read the skill file on later turns."
- After auto-compaction, Claude Code "re-attaches the most recent invocation of each skill after the summary, **keeping the first 5,000 tokens of each**."

`plan.md` measures 64,757 bytes (roughly 16–19K tokens by the usual chars-per-token heuristic; the 26K figure in the brief is a higher estimate, but the conclusion is identical either way). A 9-phase planning workflow is precisely the workload that runs long enough to trigger compaction. When it does, only the first ~5,000 tokens survive — the preamble, Step 0, and Phases 1–2 — and the instructions for Phases 5 through 9 are silently discarded from context mid-workflow, with no error. The model keeps going on a summary. Progressive disclosure fixes this structurally: each phase file is `Read` at the moment its phase begins, so it arrives as a normal tool result late in the conversation rather than as a frozen blob at turn one, and it can be re-read on demand.

**4. The decomposition fits without contortion.** Measured phase spans: preamble 141, Step 0 107, P1 26, P2 77, P3 235, P4 56, P5 371, P6 113, P7 195, P8 134, P9 74. Every phase is already under 500 lines (largest is Phase 5 at 371). A router of roughly 150–200 lines — identity block, parallel-execution strategy, Step 0 intent detection, the phase checklist, and a table pointing to the ten phase files — plus ten files that need no rewriting, only relocation.

### Concrete shape

```
skills/plan/
├── SKILL.md                    (~180 lines: identity, parallel strategy, Step 0, phase index)
└── phases/
    ├── phase-1-brainstorm.md ... phase-9-handoff.md
```

Frontmatter to carry over and add:

```yaml
description: (deepgrade) Start or resume a guided plan...   # keep; listing truncates at 1,536 chars
argument-hint: "[plan-name] [from docs/path or 'idea: description']"
allowed-tools: Read, Write, Grep, Glob, Bash, Task, ...      # keep
disable-model-invocation: true                               # ADD
```

Add `disable-model-invocation: true`. The docs name this exact use case: "Use this for workflows with side effects or that you want to control timing, like `/commit`, `/deploy`… You don't want Claude deciding to deploy because your code looks ready." A 9-phase workflow that scaffolds directories and writes documents should never auto-fire. It also removes the description from the always-on skill listing, easing the listing budget (which "scales at 1% of the model's context window" and truncates descriptions when it overflows).

### Four authoring constraints the docs impose on the split

- **One level deep, non-negotiable.** "Keep references one level deep from SKILL.md… Claude may partially read files when they're referenced from other referenced files. When encountering nested references, Claude might use commands like `head -100` to preview content rather than reading entire files, resulting in incomplete information." So `SKILL.md → phases/phase-5-audit.md` is correct; `SKILL.md → phases/index.md → phase-5-audit.md` will silently half-load. Phase 5's four embedded sub-templates (Coverage Matrix, Assumption Register, Scenario Matrix, Cross-Cutting Sweep) must stay inside `phase-5-audit.md`, not become a second hop.
- **Table of contents on the long ones.** "For reference files longer than 100 lines, include a table of contents at the top" — applies to Step 0, P3, P5, P6, P7, P8.
- **Anchor paths absolutely.** `${CLAUDE_SKILL_DIR}` resolves to "the directory containing the skill's SKILL.md file. For plugin skills, this is the skill's subdirectory within the plugin, not the plugin root," and the substitution table confirms placeholders resolve in "Skill and agent content: anywhere the placeholder appears." Prefer `${CLAUDE_SKILL_DIR}/phases/...` over `${CLAUDE_PLUGIN_ROOT}/skills/plan/phases/...` — it survives future relocation. **[UNVERIFIED — no primary source]** (Tier C, the plugin's own prior working notes): `docs/plans/2026-07-20-plugin-hardening-v5` already found that bare relative paths like `docs/planning-techniques/...` in `plan.md:609`, `plan.md:1334`, `codex-challenge.md:25`, `plan-auditor.md:137` and `plan-scaffolder.md:178` resolve against the user's project instead of the plugin cache, so those bundled frameworks never load for any installed user. Do not reproduce that bug in the phase references. Note the docs' relative-link examples (`See [FORMS.md](FORMS.md)`) are written for single-user skills; for a distributed plugin, anchor explicitly.
- **Forward slashes only.** "Always use forward slashes in file paths, even on Windows." Relevant given the Windows 11 host — write `phases/phase-1-brainstorm.md`, never a backslash variant.

### Why not the other two options in the question

Splitting into multiple namespaced commands (`/deepgrade:plan-brainstorm`, `/deepgrade:plan-audit`, …) is the wrong decomposition for a *sequential, stateful, user-initiated* workflow. It pushes phase ordering and resume logic onto the user, destroys the single-entrypoint UX that Step 0's intent-detection exists to provide, and adds ~10 entries to the `/` menu and the skill listing — which is budget-constrained and starts truncating descriptions when it overflows. Namespaced sub-commands are right for *independent* operations, which the plan phases are not.

`${CLAUDE_PLUGIN_ROOT}` is a mechanism, not an alternative strategy. It is how you point at bundled files; it does not by itself reduce SKILL.md. Used alone (Option 3) it is a legitimate cheap partial mitigation, but it leaves the file over 500 lines and does not solve the 5,000-token compaction floor.

### Sequencing

Do this as one atomic move (`git mv` the file, split, add frontmatter) rather than leaving both `commands/plan.md` and `skills/plan/SKILL.md` in the plugin — two components resolving to the same `/deepgrade:plan` invites the duplicate-entry ambiguity the prior research already flagged between `commands/doc.md` and `skills/documentation/SKILL.md`. Also note the plugin's existing test harness extracts hooks by positional index from inline `plugin.json`, and that `test-baseline.md` flags it as structurally welded to the current layout — confirm the suite does not likewise assert on `commands/plan.md`'s path before moving.

# Question 3 — Keeping duplicated reference content in sync across two shipped artifacts

## The question

What are the documented and industry-standard patterns for keeping the same reference content in two shipped artifacts (the DeepGrade Claude Code plugin bundle and the standalone troubleshooting Agent Skill) without drift — covering single-source-of-truth with a build step, git subtree/submodule, symlinks and their Windows portability limits, and CI drift-detection — and what do the Agent Skills docs say about `references/` vs `scripts/` vs `assets/` that should inform where canonical content lives?

## Recommendation

**One canonical copy inside the plugin repo, a generator that emits the standalone skill, and a CI/test-suite drift gate built on `git diff --exit-code`.** Symlinks are disqualified for this specific repo topology; submodules carry an unverified install-time risk.

### 1. What the docs actually say about references/ vs scripts/ vs assets/

The three-directory taxonomy is real but it comes from the *Agent Skills open standard* (agentskills.io/specification), not from Anthropic's own doc pages. Claude Code docs explicitly state Claude Code follows that standard. The spec defines all three as **optional, conventional — not normative**: `scripts/` = executable code the agent runs (output enters context, code does not); `references/` = documentation the agent reads on demand (REFERENCE.md, FORMS.md, domain files); `assets/` = static resources — templates, images, data files. It also permits "any additional files or directories."

Anthropic's own pages are inconsistent with the standard's plurals: best-practices shows `reference/` (singular) and flat `reference.md`; the Claude Code skills page shows flat `reference.md`/`examples.md` plus `scripts/`; the plugins reference shows `skills/pdf-processor/{SKILL.md, reference.md, scripts/}`. **`assets/` appears in none of the four Anthropic pages fetched** — only in the open standard. So directory naming is a conformance nicety, not a correctness requirement.

Applied here: DeepGrade uses `resources/`, which matches neither the standard nor any Anthropic example. Since the de-duplication work touches these files anyway, rename to the standard shape — the 9 technique docs are read-as-documentation → `references/techniques/`; the 6 doc templates in `skills/documentation/resources/` are fill-in templates → `assets/`. Cheap, but flag it as cosmetic so it isn't mistaken for a defect fix.

The load-bearing doc guidance for *where canonical content lives* is progressive disclosure: bundled files cost **zero context tokens until read**, and there is "no practical limit on bundled content." That removes any size-based argument for keeping the techniques outside the skill. Two hard constraints apply: keep file references **one level deep from SKILL.md**, and **use forward slashes only** (the best-practices page has an explicit "Avoid Windows-style paths" anti-pattern — directly relevant on this Windows 11 host). `${CLAUDE_SKILL_DIR}` resolves to the skill's own subdirectory within a plugin, so bundled-file references survive personal/project/plugin relocation.

### 2. Why symlinks are disqualified here specifically

The plugins reference does document symlinks as a sanctioned sharing mechanism, with three target-dependent behaviors: within the plugin's own directory → preserved as a relative symlink; elsewhere in the **same marketplace** → dereferenced, content copied (the meta-plugin pattern); **outside the marketplace → skipped for security**. For `--plugin-dir`/local-path installs, *only* symlinks resolving within the plugin's own directory are preserved, all others skipped.

**[UNVERIFIED — no primary source]** (Tier C, three independently verified local silent-failure modes, each of which alone kills the option):

- **Topology:** `troubleshooting-skill/` is a sibling directory *outside* `deepgrade-plugin/`, and the marketplace root is `deepgrade-plugin` itself (`marketplace.json` has `"source": "./"`). A link into the standalone skill therefore resolves outside the marketplace → **skipped by the documented security rule**.
- **Git:** `git config core.symlinks` = `false` in this repo. Per git-config, symlinks then check out as plain text files containing the link text.
- **Shell:** default Git Bash `ln -s` on this machine **silently copies** rather than links (`test -L` returns false). Only `MSYS=winsymlinks:nativestrict` produced a real symlink.

Every one of those fails *quietly* — the exact failure signature the hardening plan is trying to eliminate ("nothing errors; things quietly don't happen"). Making symlinks work would require merging both repos into one marketplace, flipping `core.symlinks`, and mandating `nativestrict` + Developer Mode for every contributor — and cross-plugin links would *still* be skipped during local `--plugin-dir` development.

### 3. Why not submodule/subtree

The plugins reference states installed plugins cannot reference files outside their directory and that marketplace plugins are **copied to `~/.claude/plugins/cache`**. Whether that copy step recurses git submodules is **not documented anywhere findable** — if it doesn't, the skill directory ships empty to every installer. That is an unverified risk with a catastrophic, silent failure mode; avoid. `git subtree` avoids it (content is genuinely committed in-tree and survives the cache copy) but sync remains a manual `subtree pull/push`, so drift returns with extra ceremony and no enforcement.

### 4. The empirical case for generation over manual sync

**[UNVERIFIED — no primary source]** (Tier C, local measurement): manual sync has already failed measurably — **all 9 of 9 technique files have drifted, 296 differing lines total.** The drift is three distinct kinds, which matters for sequencing:

- pure whitespace noise (file 08 column alignment),
- a *systematic* difference — the plugin `docs/` copies carry planning-era "Status Before Implementation" / "Implementation" sections that the skill copies don't, and which have no business being loaded into an agent's context,
- **genuine one-sided content** — file 08's skill copy has a "Backward-Compatible Fallback" section the plugin copy lacks, while the plugin copy has "Knowledge Base Structure for Correlation" the skill lacks.

That third category is the critical finding: **a naive generate-from-one-side would destroy content.** The correct sequence is reconcile once by hand (9 files, ~296 lines, a bounded one-time cost), *then* generate forward forever.

### 5. Concrete shape

Canonical source: `deepgrade-plugin/skills/troubleshooting/references/techniques/*.md` — inside the plugin repo, because that repo already owns the marketplace, the version number, the release process, and the 4-layer shell test suite. Content outside it cannot be checked by `claude plugin validate` or the existing harness.

Add `scripts/build-standalone-skill.sh` to emit the standalone artifact (copy, strip planning-only sections, rewrite SKILL.md relative links). Delete `docs/troubleshooting-techniques/`, which also retires part of the ~700 KB inert-payload backlog item. Gate it as `tests/layer5-drift-check.sh`: regenerate into a temp dir and `git diff --no-index --exit-code` against the committed standalone tree — documented git behavior is exit 0 for no differences, 1 for differences, so the gate is a one-liner with no bespoke comparison logic. Wire it into `run-all.sh` now and into GitHub Actions if/when CI is added (the repo currently has no `.github/workflows`).

This answers the plan's Open Question #3 with: **the skill-shaped copy's *content* is canonical, but its *home* moves into the plugin repo** — you keep the distilled runtime prose, drop the design-time prose, and get a single edit point that the existing test harness can enforce.

# Question 4 — Versioning, marketplace caching, user-side updates, and what counts as a breaking change

## The question

For a Claude Code plugin distributed via a marketplace: how do version numbers, `marketplace.json` vs `plugin.json` version fields, caching, and user-side updates actually work — and what counts as a semver breaking change for a plugin (moved hooks, renamed agents, removed commands)?

## How it actually works (Tier A, from code.claude.com)

Note: every `docs.claude.com/en/docs/claude-code/*` plugin URL now 301-redirects to `code.claude.com/docs/en/*`. Any hardening doc citing the old paths should be updated.

**1. Yes — marketplace plugins are copied to a cache, not used in place.** "For security and verification purposes, Claude Code copies *marketplace* plugins to the user's local **plugin cache** (`~/.claude/plugins/cache`) rather than using them in-place." The layout is `cache/<marketplace>/<plugin>/<version>/...` — the version string is literally part of the path. "Each installed version is a separate directory in the cache. When you update or uninstall a plugin, the previous version directory is marked as orphaned and removed automatically 7 days later." Consequences for DeepGrade: paths escaping the plugin root (`../shared-utils`) break after install, and `${CLAUDE_PLUGIN_ROOT}` changes on every update — so nothing durable may be written there. Use `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/deepgrade-<marketplace>/`) for state that must survive updates.

**2. Version resolution — and the trap DeepGrade is currently sitting in.** Resolution order is: (1) `version` in `plugin.json`, (2) `version` in the marketplace entry, (3) the git commit SHA (for `github`, `url`, `git-subdir`, and relative-path sources in a git-hosted marketplace), (4) `unknown`. The docs warn explicitly: "Avoid setting `version` in both `plugin.json` and the marketplace entry. Claude Code always uses the `plugin.json` value **without warning**, so a stale manifest version can mask a version you set in `marketplace.json`."

**[UNVERIFIED — no primary source]** (Tier B, local inspection — see evidence 4.6): DeepGrade sets `"version": "4.31.0"` in **both** files. They agree today, so nothing is broken right now — but this is a latent trap: a maintainer who bumps only `marketplace.json` ships nothing to anyone, silently. `claude plugin validate .` warns when the two disagree, which is the only guardrail.

**3. A version bump is the *only* thing that forces an update.** "Claude Code uses the plugin's version as the cache key that determines whether an update is available… Claude Code computes the current version and skips the update if it matches what's already installed." With an explicit version set: "Pushing new commits without bumping it has no effect, and `/plugin update` reports 'already at the latest version'." For a hardening plan this is the single most important operational fact: **a security fix to a DeepGrade hook reaches zero existing users unless `plugin.json` version changes.** Git history, tags, and marketplace refreshes are all irrelevant to the cache key.

**4. Documented user-facing update procedure** (in order):

- `/plugin marketplace update <marketplace-name>` — refreshes the catalog from source. A marketplace added with a branch/tag `ref` updates to the latest commit of that ref, not the default branch.
- `/plugin update <plugin>` (or `claude plugin update <plugin>`, `--scope user|project|local|managed`, default `user`).
- `/reload-plugins` — to apply without restarting.
- Verify with `/plugin list` (shows version, source marketplace, enable status).

**Auto-update:** "Official Anthropic marketplaces have auto-update enabled by default. Third-party and local development marketplaces have auto-update **disabled** by default." So DeepGrade users are on manual updates unless they opt in via `/plugin` → Marketplaces → Enable auto-update. When enabled, Claude Code checks "after your session starts, with a random delay of up to ten minutes," then notifies the user to run `/reload-plugins`. Global kill switch: `DISABLE_AUTOUPDATER`; `FORCE_AUTOUPDATE_PLUGINS=1` keeps plugin updates while disabling CLI updates.

**Mid-session update semantics matter for DeepGrade specifically**, because it ships hooks: "When a plugin updates mid-session, hook commands, monitors, MCP servers, and LSP servers keep using the previous version's path. Run `/reload-plugins` to switch hooks, MCP servers, and LSP servers to the new path; monitors require a session restart." Also: `SKILL.md` edits take effect immediately, but `hooks/`, `agents/`, `.mcp.json`, and `output-styles/` changes do **not** until reload.

**5. What counts as breaking.** The docs are explicit on exactly one thing and silent on the rest — the two are separated below.

*Documented (Tier A):* the plugin `name` is the stable identifier. "Users reference it in `enabledPlugins`, `pluginConfigs`, and `/plugin install` commands, so changing it breaks every existing install." Use `displayName` to change the UI label without breaking installs. # Question 5 — Referencing optional MCP tools in subagent `tools:` and command `allowed-tools:` frontmatter

## The question

How must MCP server tools be referenced in Claude Code subagent `tools:` frontmatter and slash-command `allowed-tools:` frontmatter — exact identifier format, behavior when a listed tool does not resolve, and the recommended pattern for a plugin (DeepGrade v4.31.0) that OPTIONALLY benefits from MCP servers it does not bundle?

## Recommendation

### Format (Tier A, unambiguous)

MCP tools are referenced by their fully-qualified callable name, never the bare tool name. For a user-configured server: `mcp__<server>__<tool>`. For a server bundled inside a plugin: `mcp__plugin_<plugin-name>_<server-name>__<tool-name>`, with every character outside `A-Z a-z 0-9 _ -` replaced by `_`. The MCP docs state this name is what you use "in permission rules, a skill's `allowed-tools` list, a subagent's `tools` field, or a hook matcher" — one identifier, all four call sites. Server-level wildcards `mcp__<server>` and `mcp__<server>__*` are also accepted in subagent `tools:`/`disallowedTools:`; `mcp__*` works only in `disallowedTools`.

### Resolution failure — the critical asymmetry between the two fields

Subagent `tools:` is an **allowlist**: omitted means inherit every tool including MCP tools; present means the agent gets exactly what resolves. Partial non-resolution is tolerated silently — the agent launches with the subset that resolved. Only if NOTHING in the list resolves does Claude Code refuse to launch the subagent and return an error naming the entries (v2.1.208+; before that it launched tool-less and returned confusing empty results).

Slash-command/skill `allowed-tools:` is **not a restriction at all** — it is a one-turn permission pre-approval. The docs are explicit: "It does not restrict which tools are available: every tool remains callable." So an unresolvable entry there is a harmless no-op, while an unresolvable entry in a subagent `tools:` allowlist is a permanent, silent capability loss.

### DeepGrade is currently broken on exactly this

Two agents list bare, unprefixed MCP names in their allowlist:

- `C:/Users/NewAdmin/Projects/plugin/deepgrade-plugin/agents/dependency-mapper.md` — `tools: Read, Grep, Glob, Bash, ref_search_documentation, ref_read_url`
- `C:/Users/NewAdmin/Projects/plugin/deepgrade-plugin/agents/integration-scanner.md` — `tools: Read, Grep, Glob, ref_search_documentation, ref_read_url`

Those two names can never resolve — no `mcp__` prefix, no server segment. The built-ins resolve, so the agents launch normally and nobody sees an error; they have simply never had the research capability their prompts assume. Three commands carry the same bare names in `allowed-tools:` (`commands/doc.md`, `commands/plan.md`, `commands/troubleshoot.md`) where they are inert no-ops.

**[UNVERIFIED — no primary source]** (Tier C, local command run): `claude plugin validate` on this plugin returned "Validation passed with warnings" (one cosmetic marketplace-description warning) — the validator checks frontmatter schema, not tool resolution, so this class of defect will never be caught by CI.

### Why you must not simply "fix" the names

The obvious repair — rewrite them as `mcp__Ref__ref_search_documentation` — is wrong, and this is the crux of the whole question. The server segment comes from the key the **installing user** chose in their own `.mcp.json` or connector config. **[UNVERIFIED — no primary source]** (Tier C, observed in this session's own tool roster): on this very machine the Ref server is registered as `claude_ai_Ref_MCP`, so the real name is `mcp__claude_ai_Ref_MCP__ref_search_documentation`; another user running the same plugin may have `ref`, `Ref`, or `ref-tools`. A plugin that does not bundle the server cannot know the identifier, so any hardcoded MCP name in a distributed plugin is a guess that silently fails for most installs. Hardcoding is strictly worse than omitting, because in an allowlist it buys nothing while creating the false impression of capability.

### Recommended pattern — Option A: invert the two research agents from allowlist to denylist

Replace `tools:` with `disallowedTools: Write, Edit` on `dependency-mapper.md` and `integration-scanner.md`. The docs describe this exact case: a subagent with `disallowedTools` "inherits every tool from the main conversation except Write and Edit. The subagent keeps Bash, MCP tools, and everything else."

This gives true graceful degradation with zero name-guessing: a user who has Ref/Exa/Perplexity connected gets those tools inherited automatically under whatever names they use, and a user with none simply has fewer tools while the built-in WebSearch/WebFetch fallback in `skills/mcp-research/SKILL.md`'s tiered strategy takes over. The read-only posture the scanners depend on is preserved by the denylist. Keep the prose-level degradation contract in the agent bodies as the behavioral guarantee, since inheritance is best-effort, not a hard promise. Strip the bare names from the three commands' `allowed-tools:` in the same pass as dead-code cleanup, and add a repo grep guard rejecting any tool token matching `^(ref_|web_search_exa|get_code_context_exa|perplexity_)` outside prose, since `claude plugin validate` will not do it for you.

### Do not bundle a `.mcp.json` for Ref/Exa/Perplexity

Those are third-party hosted services requiring the user's own API keys; bundling forces a per-server approval prompt on every install, adds tool-description context cost to every session for users who never research, and cannot ship credentials anyway. Bundling is the right call only for a server you actually author and control.

### One honest caveat on Option A

Anthropic issue #13605 ("Custom plugin subagents cannot access MCP tools (built-in agents can)", closed, labeled bug/has-repro) reports that plugin-defined subagents historically received no MCP tools in ANY configuration — omitted `tools:`, wildcard, or explicit name — while built-in agents like `general-purpose` did. The issue is closed, but it could not be verified from official docs which release fixed it, nor confirmed on Windows. Treat inherited MCP access as an upside that may or may not materialize, never as a dependency. Option A is still correct under that uncertainty, because it is exactly as good as Option B when inheritance is broken and strictly better when it works.

Also note plugin subagents ignore `mcpServers`, `hooks`, and `permissionMode` frontmatter entirely for security reasons — so per-agent MCP scoping is simply not available to DeepGrade and should not be attempted.
